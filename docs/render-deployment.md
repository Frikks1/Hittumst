# Render and AWS deployment

Prepared 2026-09-21. These files do not create accounts or deploy anything. The application still requires all release gates, real provider credentials, staged verification and store review.

## Topology

`render.yaml` defines four Frankfurt Docker services: production web (1 CPU/2 GB), production continuous worker (1 CPU/2 GB), staging web (0.5 CPU/512 MB) and staging continuous worker (1 CPU/2 GB). Auto deployment is off. The one worker per environment runs media, account deletion, commerce, billing reconciliation, push and voice concurrently; each queue retains its existing database claims/leases. A queue cycle drains up to ten batches or ten minutes, then yields; continuing backlogs resume after 250 ms rather than waiting the full idle interval. No Vercel cron or GitHub mutation schedule remains. The manual GitHub workflow only observes readiness.

`Dockerfile` installs FFmpeg/FFprobe, builds Next standalone plus the dedicated worker, and runs as an unprivileged user. Web runs `node apps/admin/server.js`; worker runs `node apps/admin/dist-worker/worker.mjs`. A worker does not expose an HTTP listener. The public web service rejects direct scheduled-job execution when Render owns scheduling. Voice runs every 10 seconds; media polls after 5 seconds, deletion after 15, commerce/billing after 30 and push after 60. Voice stays disabled until both server configuration and database capability approval are complete.

Local packaging was verified on 2026-09-21 with `node scripts/check-docker-runtime.mjs` (15/15 checks; `artifacts/operations/docker-runtime.json`). This builds the real image with synthetic public values and exercises standalone public HTML, CSS/JavaScript assets, liveness, readiness authorization, finance login protection, worker dependency loading and FFmpeg/FFprobe. Containers run without external network or host ports, with a read-only filesystem and dropped capabilities. Hosted credentials, load and external service behavior require separate acceptance.

## Initial setup

For the first staging deployment, use **Blueprint Path `render.staging.yaml`** on branch `main`. It creates only `hittumst-staging-web`, `hittumst-staging-worker` and their environment group in Frankfurt. The existing `render.yaml` includes production as well and should not be used for initial staging-only provisioning. Do not create a second Blueprint managing the same staging resources; when production is ready, either expand the existing Blueprint or prepare a separate production-only file. Service auto-deploy is disabled, but initial Blueprint deployment still provisions resources. To control configuration updates manually too, set the Blueprint's **Auto Sync** to **No**.

1. Create separate Supabase projects for production and disposable synthetic staging. Select the agreed EU region; preserve/reconcile any existing hosted database before applying migrations. Follow `database-reconciliation.md`. Apply the current migrations and deploy the Edge Functions. Do not copy production member data into staging.
2. Create the Render Blueprint from `render.staging.yaml` for staging, or the reviewed production configuration when ready. Before deploying, securely fill each applicable named environment group (`hittumst-staging`, `hittumst-production`) with its own values listed below. The Blueprint creates defaults and random worker secrets; it deliberately omits account credentials. Render ignores `sync:false` inside environment groups, so group secrets must be entered in the Dashboard or approved secret provisioning flow. New service instances fail closed until configuration is complete. [Render Blueprint reference](https://render.com/docs/blueprint-spec).
3. Configure the transient moderation bucket from `aws-media-moderation.yaml` in `eu-central-1`. Create a dedicated worker credential and attach only its generated managed policy. The template blocks public access, encrypts objects, requires TLS and scopes S3 access to `moderation/`. Rekognition actions are region constrained. Configure AWS data-use/privacy settings and review the processor agreement before setting `AWS_MEDIA_PRIVACY_VERIFIED=true`.
4. Supply identical public build values to the web and worker builds for that environment. Render Docker environment variables are available as build arguments only when the Dockerfile declares them. Never introduce a server key or provider secret as an `ARG` or `NEXT_PUBLIC_` variable. Build/deploy staging, then verify health, pipelines and rollout with synthetic accounts.
5. Run the staged tests, workload, deletion and recovery drills. Configure monitoring and verify the owner and backup actually receive failures. Only then promote the same reviewed revision with the separate production environment values.

`HITTUMST_APP_ENV`, `WORKER_SCHEDULER=render` and service-specific `WORKER_EXECUTION_ROLE` are supplied by the Blueprint. The staging group requires `STAGING_SYNTHETIC_DATA_CONFIRMED=true`. The server deliberately sends no raw stack frames, so minimal alerts work without source maps. The worker logs only fixed codes and numeric aggregate counters.

## Health and response

- `GET /api/operations/live`: public process liveness, no project/member data. This is Render's restart/deploy check, not proof the backend or workers work.
- `GET /api/operations/health` with `Authorization: Bearer <CRON_SECRET>`: configuration identity for the environment/project reference.
- `GET /api/operations/ready` with the same bearer: real DB connectivity, fixed queue counts, failed/late jobs and six worker heartbeats. HTTP 503 indicates missing/stale/failed workers or overdue/failed queues. It returns no identifiers, paths, message bodies or provider responses. General heartbeat freshness is 120 seconds; voice is 30 seconds. A worker must also have completed a successful cycle within 20 minutes.

Set an external authenticated uptime monitor to request `/api/operations/ready` every 60 seconds, alert on two failures, and notify the pilot owner plus backup. Do not put bearer tokens into URL query parameters. Configure Sentry's fixed-code alert delivery and Render deployment/process alerts. Simulate a stopped worker, failed raw cleanup, unavailable backend and recovered queue. Record alert delivery and acknowledgement times. The manual GitHub observation is additional diagnostics and does not replace missed-worker alerting. Billing/voice intentionally remain red while the intended feature is disabled or unconfigured.

AWS objects are deleted immediately after moderation. The bucket lifecycle is a fallback after failed deletion, with eligibility after one day and asynchronous AWS execution; it is not an exact 24-hour guarantee. Inspect/delete stranded copies during incidents. The bucket is not a backup and should not have versioning/replication enabled. Operator approval of retention and provider privacy settings remains required.

## Capacity workload

Use an otherwise isolated synthetic staging project with operational media/deletion workers and reviewed Hittingar configuration. The harness refuses any existing Auth email outside `@example.test`; never weaken its guards. Supply these values through a secure environment, not command arguments: `STAGING_WORKLOAD_PROJECT_REF`, `STAGING_WORKLOAD_URL`, `STAGING_WORKLOAD_PUBLISHABLE_KEY`, `STAGING_WORKLOAD_SECRET_KEY`, `STAGING_WORKLOAD_SYNTHETIC_CONFIRMED=true`, `STAGING_WORKLOAD_ALLOW_WRITES=true`.

Run `node scripts/staging-workload.mjs --smoke` first. It creates 12 accounts and 4 published events with 10 concurrent users for 30 seconds. A successful smoke report explicitly cannot satisfy the capacity gate. Then run `node scripts/staging-workload.mjs`: 1,000 synthetic accounts, 200 independently hosted published events, 100 concurrent users and 30 minutes of mixed authenticated reads and message writes. It also uploads quarantined media and checks that even the uploader cannot download unprocessed bytes, validates recipient Realtime delivery and observes foreign subscriptions for leaks.

Engineering acceptance defaults are p95 read <750 ms, write <1,000 ms, Storage workflow <5,000 ms and Realtime delivery <2,000 ms, <1% read/write/Storage errors, and zero privacy or Realtime delivery misses. These are explicit starting SLOs, not measured production claims. Failed setup, missing operation samples, failed normal account-deletion cleanup or insufficient duration prevent passing. The script never changes RLS, Auth limits, subscriptions or feature gates to make a run pass.

Accounts are cleaned up through the real account-deletion queue and must disappear within the ten-minute cleanup deadline. `tmp/capacity-fixtures-<run-id>.json` records only synthetic fixture IDs for interrupted-run investigation. If a process is killed before cleanup, identify that exact `capacity-<run-id>-...@example.test` set and complete normal deletion; do not delete all staging accounts or clear unrelated queues. `tmp/staging-workload-result.json` contains aggregate evidence only. Tokens/passwords are never written. Keep the private fixture journal out of submitted release evidence.

## Encrypted object backup and restore rehearsal

`scripts/media-recovery.mjs` implements encrypted backups of approved, still-referenced profile photos/videos, album files/thumbnails, messages and meetup media. The service-only paged recovery RPC excludes quarantine, unapproved profile media, deleted messages/albums/events and accounts with deletion requested. It does not expose a member-facing media inventory. The encrypted manifest and each object use AES-256-GCM with fresh nonces; SHA-256 checks verify restored bytes. Filenames are random and object paths stay inside the encrypted manifest.

Before backups, initialize the independent journal as described below. For `node scripts/media-recovery.mjs backup`, securely supply `MEDIA_BACKUP_SOURCE_PROJECT_REF`, `MEDIA_BACKUP_SOURCE_URL` (exact HTTPS Supabase origin, no trailing slash), `MEDIA_BACKUP_SOURCE_SECRET_KEY`, `MEDIA_BACKUP_SOURCE_APPROVED=true`, a new `MEDIA_BACKUP_DIRECTORY` and `MEDIA_BACKUP_ENCRYPTION_KEY` (32 random bytes encoded as 64 hex characters). The parent directory must exist; an existing backup directory is never overwritten. Store encryption keys separately from the encrypted archives. The script writes no plaintext media or manifest. An interrupted archive without `manifest.enc` is not a completed backup. Copy completed ciphertext to the approved off-site store with an independently tested retention policy; local disk alone is not a disaster-recovery backup.

For `node scripts/media-recovery.mjs restore`, keep the original source configuration/key/archive, and supply `MEDIA_RESTORE_TARGET_PROJECT_REF`, `MEDIA_RESTORE_TARGET_URL`, `MEDIA_RESTORE_TARGET_SECRET_KEY`, `MEDIA_RESTORE_TARGET_SYNTHETIC=true`, `MEDIA_RESTORE_TARGET_QUARANTINED=true`. Restore the matching synthetic database snapshot first and keep all target member access, workers and schedules disabled during the drill. The target must differ from the source/known production project and contain only `@example.test` Auth accounts. The script first quarantines all restored accounts, revokes their sessions and refresh tokens, verifies that source/target signing keys differ, and loads the independent deletion journal. It rejects account/object tombstones even if the restored database says the media is active. It then freshly checks both live canonical source and target references for every file before upload and again after verification; a deletion during upload removes that newly restored copy. Existing mismatched objects cause failure, and uploads never overwrite. Operator reports contain counts/status only.

This provides a deletion-aware connected-source rehearsal, not unattended source-loss recovery. If the canonical source is unavailable, the tool fails closed. The independent account-deletion journal outside the PITR boundary is implemented. Off-site archive scheduling/retention, source-loss restore, final cutover and legal-held evidence recovery still require configuration and a real drill. Keep the restore target quarantined until a final deletion reconciliation and owner-reviewed cutover. No production restore command is supplied.

## Independent deletion journal and quarantine

Provision aws-media-backup.yaml in Frankfurt as a separate bucket from moderation. Set the owner-approved BackupRetentionDays; its lifecycle applies only to encrypted backups/. Deletion tombstones have no automated expiry because they must outlive every recoverable backup. Review this retention policy before public launch. Attach DeletionPublisherPolicy to the worker and use the separate RecoveryOperatorPolicy for backup/restore administration. Neither grants deleting tombstones. Never reuse the moderation bucket.

Supply MEDIA_BACKUP_BUCKET, MEDIA_BACKUP_KEY_ID (a stable nonsecret key label), MEDIA_BACKUP_ENCRYPTION_KEY (64 hex characters), AWS_REGION=eu-central-1 and appropriately scoped AWS credentials. Initialize a new project/key once with node scripts/media-recovery.mjs initialize-journal using the source project configuration and MEDIA_BACKUP_SOURCE_APPROVED=true. This publishes and verifies an encrypted initialization marker. No initialization or journal write was performed during this development task. Workers fail closed until this marker and matching key are available. Keep historical journal encryption keys in the secure key store; recovery accepts the secret MEDIA_BACKUP_OLD_KEYS_JSON object mapping other key labels to 64-character hex keys and fails if any journal generation cannot be decrypted. Never copy that value into an issue or artifact.

Before removing any account bytes or Auth identity, the worker appends an AES-256-GCM tombstone containing account/job identifiers and the current claimed object list, then reads it back and verifies its content. Keys use a digest of account/job/manifest identity. If a claim changes after partial cleanup, a new immutable record preserves both manifests; an identical retry reuses the verified record. Failed publication/readback leaves the deletion job retryable and the member's access revoked. A crash after publication but before deletion acknowledgement remains safely replayable.

Restore reads every key generation from the independent bucket and refuses missing initialization, unknown keys, malformed/undecryptable records, truncated listings, backup/journal project mismatch and conflicting existing object bytes. The target database additionally quarantines all restored accounts, rejects new Auth sessions and revokes old sessions/refresh tokens. There is no automatic account reenable operation. The script verifies different current asymmetric signing keys between source and target; legacy or unverifiable signing state blocks the drill.

A crash can still occur after the original database deletion request and before journal publication. That unpublished in-flight request cannot be inferred reliably from a rolled-back database. The tool therefore requires reachable current canonical eligibility for each object and keeps every restored account quarantined; unavailable or unverified evidence never reopens it. Individual media deletions outside account deletion also rely on the fresh canonical inventory. Reopening accounts requires a separate reviewed cutover with current account ownership/access verification, signing-key rotation as needed and final journal reconciliation. The planned 8-hour RTO / 24-hour RPO remains a drill target, not a verified recovery promise.

The deletion-journal bucket policy requires `If-None-Match` for every journal object write; the worker role can publish records but cannot initialize the journal. Initialization uses the separate recovery role. This enforces create-only writes in S3 as well as in the publisher code ([AWS conditional-write policy](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html)). Recovery verifies each record's object-key digest against its encrypted account/job/object identity.

On this Windows development machine, `node scripts/rehearse-database-release.mjs` coordinates the final local clean-install, real-service, logical-restore and preserved-baseline upgrade checks. Run it only while no other local database tests are active. It checks the local Docker project and synthetic source before resetting, strips hosted service-test overrides, and writes aggregate evidence to `artifacts/operations/database-release-rehearsal.json`; detailed local logs stay under `tmp`. The CI database matrix performs the corresponding clean and upgrade runs on Linux. This is not hosted recovery evidence.
